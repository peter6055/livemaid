# LiveMaid Features & Implementation Truths

This document serves as the source of truth for the implemented features and architectural decisions in LiveMaid.
**ALL AGENTS MUST READ THIS DOCUMENT before making changes to ensure existing features are not accidentally broken.**

## 1. Diagram Types & Two-Way Sync

- **Supported Two-Way Sync**: `flowchart` (and `graph`), `sequenceDiagram`, and `classDiagram`. These diagrams allow visual editing (e.g., double-clicking text, adding nodes via buttons, editing class members in the property panel) which automatically updates the underlying Mermaid code.
- **Visual-Only (One-Way Sync)**: All other Mermaid diagram types. These render correctly but are read-only on the canvas. Users must edit the code directly to change them.
- **Implementation**: The `determineDiagramType` function in `src/lib/diagrams/utils.ts` determines the type. For class diagrams it returns `"classDiagram"` (the regex-matched header keyword); the plugin is registered under that exact key in `src/lib/diagrams/registry.ts`. Features like the Quick Add Node button rely on this type to know what code to append.

## 2. Pan & Zoom Engine (`react-zoom-pan-pinch`)

- **Infinite Canvas (Mouse Dragging)**: We use `react-zoom-pan-pinch`. We explicitly set `limitToBounds={false}`. This is **CRITICAL** because without it, the library locks panning when the diagram fits entirely within the view, breaking the ability to drag the canvas with the mouse.
- **Wheel Config**: `wheel={{ wheelDisabled: true, step: 0.05 }}` is used on the main editor canvas to prevent accidental wheel-zoom while editing.
- **Trackpad Interaction**: Trackpad panning remains enabled (`trackPadPanning={{ disabled: false }}`), and zoom is performed through the zoom controls and pinch gestures.
- **Trackpad Swipe Navigation Guard**: The app globally applies `overscroll-behavior-x: none` on `html` and `body` to block browser-level horizontal swipe navigation (back/forward page changes) while using trackpad gestures.
- **Zoom Constraints**: We set `minScale={0.5}` and `maxScale={50}`. The `minScale` limit prevents diagrams from zooming out into tiny, unreadable, or lost shapes.
- **Interaction Locks**: `panning={{ disabled: isInlineEditing || dragState?.isDragging }}` is set to prevent the canvas from moving while the user is typing in the inline editor or dragging sequence elements.

## 3. Interactive Node Selection & Editing

- **Node Resolution (`getClickedNode`)**: When a user clicks the canvas, we traverse up the DOM tree from the `e.target` to find a container with the `.node` or `.cluster` class.
- **ID Normalization**: Mermaid injects dynamic prefixes (e.g. `flowchart-mermaid-svg-1234-`). The `getClickedNode` function cleans this raw SVG ID into a clean ID (e.g., `A`) that matches the actual Mermaid code. Both `rawSvgId` and `cleanId` are returned.
- **Selection Box**: We calculate the bounding box of the `.label`, `foreignObject`, or `text` inside the node and apply the current zoom `scale` to render a perfectly aligned selection outline.
- **Layout Alignment Observers**:
  - **compilation tracking**: Since Mermaid compilation is asynchronous, we hook selection recalculation directly to changes in both `code` and `svgContent` (the compiled output in the DOM) using a 50ms layout timeout.
  - **ResizeObserver**: To ensure that the selection box and text edit overlays remain glued to the target node during screen resizing or split-panel dragging, we mount a `ResizeObserver` observing both `containerRef.current` and `.mermaid-container`.
- **Dynamic Style Highlights**: The floating style bar queries the raw Mermaid styling code using a static regex scraper (`getStyleFromCode`) alongside native `window.getComputedStyle(element)` queries to dynamically toggle active outlines on preset background/border/text colors and bold/italic font states.
- **Node Styling Reset**: Clicking the Reset Style button in the `NodeManipulationToolbar` completely purges all `style <nodeId>` lines from the raw Mermaid source. This completely reverts custom background color, border color, text color, font weight, and italic traits, immediately forcing the node to adhere back to the active diagram theme.
- **Mermaid Style Color Sanitization Guard**: Before persisting editor code, style lines are sanitized so `rgb(...)` / `rgba(...)` color tokens are converted to Mermaid-safe `#RRGGBB` values. This prevents parse failures caused by comma-delimited CSS colors inside `style <id> ...` declarations and auto-heals previously saved invalid style lines.
- **Physical Size Zoom Locking**: The floating styling bar (`NodeManipulationToolbar`), inline formatting toolbar, inline textarea overlay, and Quick Add (+ Button) employ real-time, zero-lag DOM-level scale-locking (via attributes `data-scale-lock` and `data-base-transform`) inside react-zoom-pan-pinch's `onTransformed` and `onInit` callbacks. This completely bypasses React render delay and Safari's CSS variable transition limitations, guaranteeing a perfectly locked physical sizing.
- **Clamped Scale-Lock (`data-scale-lock-max1`) — constant when zooming IN, proportional when zooming OUT**: A variant of the above for on-canvas affordances that should NOT keep a fixed screen size at extreme zoom-OUT. `updateScaleLockedElements` applies `scale(min(1, 1/zoom))` to `[data-scale-lock-max1]` elements (vs the plain `scale(1/zoom)` for `[data-scale-lock]`). Effect: when zoomed IN (zoom > 1) the element counter-scales DOWN to a constant on-screen size (never balloons); when zoomed OUT (zoom < 1) the clamp pins the factor at `1×` so the element SHRINKS WITH the diagram instead of staying a fixed screen size that dwarfs a densely-packed, zoomed-out diagram. Used by the message endpoint drag bars (see §15) — at min zoom (0.5×) a plain scale-locked 44px bar spanned ~8 message rows and dominated; with the clamp it renders ~22px and fits the message band. Any `[data-scale-lock-max1]` element must ALSO be listed in the two `hitFloatingUi` guards (the document-capture mousedown guard and the canvas `onDoubleClick` guard) so its presses are treated as floating UI and never leak into canvas hit-testing/deselection.
- **Decoupled Selection Outlines**: The selection box container does NOT receive scale transforms (leaving its width, height, left, and top coordinates perfectly matching the node in SVG coordinates), while its border and shadow thicknesses are separately scale-locked using `data-scale-lock-border` and `data-scale-lock-shadow`. This prevents selection box distortion or misalignment at any zoom depth.
- **Auto-Deselection on Zoom**: To ensure a clean, distraction-free workspace and prevent layout scaling clutter during navigation, zooming in, zooming out, resetting transform, or starting a trackpad pinch-zoom gesture automatically deselects any currently active selection. This instantly closes the `NodeManipulationToolbar` and floating controls, immediately focusing interaction back on the canvas.
- **Flowchart Node Hover Highlight**: On `mousemove`, when the canvas is in `flowchart`/`graph` mode, `useCanvasInteraction` detects the hovered `.node` SVG element via `e.target.closest('.node')`, measures its viewport bounding rect, and converts to canvas-space coordinates using `(rect.* - containerRect.*) / scale`. This is stored as `hoveredFlowchartNodeBox` (state in the hook, propagated through `EditorCanvas` props). `EditorCanvas` renders a thin `border-indigo-400` overlay div (`pointer-events: none`, `z-[19]`, 1.5px border scale-locked) around the hovered node. The highlight is suppressed during inline editing, active connection drawing, and selection-box creation.
- **Rename Button in Node Toolbar**: `NodeManipulationToolbar` exposes an optional `onEditLabel?: (e: React.MouseEvent) => void` prop. When provided, a `Pencil` icon button is rendered as the first item in the toolbar (before color pickers). Clicking it calls `handleEditClick` in `EditorCanvas`, triggering the same inline text editor flow as a physical double-click. This gives users a discoverable affordance for renaming a node without requiring a precise double-click gesture.
- **Unified Interaction State Machine (IDLE / SELECT_MODE / EDIT_MODE)**: Canvas interaction is centralized in `useCanvasInteraction` with strict transitions and a capture fallback in `EditorCanvas`:
  - **IDLE → SELECT_MODE**: single click on node/edge selects it and shows the floating toolbar.
  - **Double-click edit entry (robust path)**: double-click is detected in `handleSvgClick` via `e.detail >= 2` when the clicked element matches `selectedNodeIdRef.current`; this calls `handleEditClick` and enters EDIT_MODE.
  - **Document capture fallback for single-click reliability**: `EditorCanvas` registers a `document.addEventListener('mousedown', ..., true)` listener and routes a synthetic event (including `detail`, `clientX`, `clientY`) into `handleSvgClick`. This is required because Mermaid SVG + `foreignObject` content can bypass normal React bubbling on single-click in some paths.
  - **Cross-element single-click while editing**: clicking node B while editing node A commits A (`commitEditRef.current?.()`), exits EDIT_MODE, and transitions directly to SELECT_MODE on B.
  - **Cross-element double-click while editing**: commit current edit, transition selection, then allow immediate re-entry to EDIT_MODE on target via click-detail path.
  - **Outside click → IDLE**: clicking empty canvas clears selection and exits overlay state.
  - **`commitEditRef`**: a `useRef` slot in `useCanvasInteraction` that `LiveMaidEditor` fills with `handleEditSubmit`, enabling commit-before-transition without stale closure issues.
  - **No-op commit guard**: `handleEditSubmit` exits early if new text does not change Mermaid code, preventing unnecessary recompiles and layout drift.
  - **Debug logging (opt-in only)**: click diagnostics are behind `window.__LM_DEBUG_CLICKS = true` or `localStorage['livemaid:debug-clicks']='1'`; default runtime is quiet.

## 4. Inline Text Editing (The Overlay)

- **Overlay Positioning**: When a user double-clicks a node, an absolute-positioned `<textarea>` is rendered on top of the diagram. It calculates its exact position and size based on the SVG element's bounding box.
- **Hiding Original Text**: To avoid double text (seeing the SVG text behind the textarea), we inject a dynamic `<style>` tag that sets `opacity: 0 !important` on the specific `#${selectedSvgId} .label, text, foreignObject` while editing is active.
- **Event Propagation (CRITICAL)**: All overlay UI elements (toolbar, textarea) MUST have `onMouseDown={(e) => e.stopPropagation()}` and `onClick={(e) => e.stopPropagation()}`. If this is missed, clicking the overlay will trigger the canvas pan/zoom handlers underneath and steal focus or cause jitter.
- **High-Contrast Text Highlight Selection**: To guarantee that selected/highlighted text remains visible in all OS/browser color themes (preventing dark-mode overrides from rendering selected text invisible), the overlay input explicitly enforces high-specificity indigo selection styles: `selection:bg-indigo-600 selection:text-white`.
- **Spacious Width Boundaries**: To prevent premature wrapping and make long typed words fully legible, the overlay textarea calculates its unscaled target width as `Math.min(Math.max(textBox.width + 200, 350), 700)`.
- **Drift-Free Viewport Coordinate Bounds**: Hover elements, overlays, and context menus (like `shapePicker`) that render in the static viewport space must calculate coordinates by subtracting `.getBoundingClientRect()` of the closest static container (`.relative.overflow-hidden`) rather than the zoomed/panned inner canvas (`containerRef.current`). This guarantees 1:1 screen-to-cursor matching with absolute precision under any zoom or pan level.

## 5. Quick Add Node (+ Button)

- **Visibility**: Appears below the selection box when a node is selected (and inline editing is not active).
- **Code Generation (`handleAddNodeFromSelected`)**:
  - For flowcharts: Appends `\n {selectedNodeId} --> NewNode{i}[New Node]`. It auto-increments the `i` to avoid ID collisions.
  - For sequence diagrams: Appends `\n {selectedNodeId}->>NewActor: new msg`.
- **Sequence UX Rule**: In sequence diagrams, the selected-node quick-add `+` control is hidden to prevent click-to-add creation from the selection box. Sequence creation remains available through lifeline anchor `+` handles via drag-to-connect interactions.

## 6. Theme Management

- We manually inject or update the Mermaid configuration block (`--- \n config: \n theme: 'dark' \n ---`) at the top of the raw Mermaid code string to control themes. This ensures the theme is persisted directly in the diagram code itself.

## 9. Flowchart Edge/Connector Styling & Label Editing

- **Interactive Edge Selection**: Users can click directly on a flowchart link (edge path) or its text label. The editor identifies the adjacent `.edgeLabel` node, snaps the coordinates to the label, and assigns it a queryable dynamic ID (`edge-label-${cleanId}`).
- **Strict Parallel Edge Isolation (Hover & Selection)**: Mermaid v11+ automatically injects a unique, canonical `data-id` attribute containing the exact path ID (e.g. `L_src_dst_index`) on the `<g class="label">` container inside _every_ `.edgeLabel` container (both labeled and unlabeled). We map hover highlight and click selection strictly using these canonical IDs instead of array index fallbacks (`edgeLabels.indexOf`). This completely eliminates index-drift, ensuring that hover isolation and selection are strictly isolated to individual parallel edge occurrences without parallel leakage or mapping drift.
- **Unlabeled Edge Bounding Box Snapping**: If an edge has no label, its `.edgeLabel` container exists but contains empty text and has zero width/height. To prevent the selection overlay from collapsing or flying to `(0, 0)`, coordinates for unlabeled edges are measured directly from the visual `<path.flowchart-link>` bounding box rather than snapping to the empty label container.
- **Edge Manipulation Toolbar**: When an edge is selected, a dedicated scale-locked floating toolbar appears on the canvas. It provides quick controls for:
  - **Arrow Style**: Configures the connector arrowhead (plain, arrow, double arrow, cross, double cross, circle, double circle).
  - **Stroke Style**: Configures the link dash pattern and weight (solid, dashed, thick).
  - **Bidirectional Style Coercion for Thick & Unsupported Connectors**: Mermaid does not natively support thick variants for cross (`--x`) or circle (`--o`) arrowheads. To prevent compilation/syntax errors:
    - **Stroke to Thick**: If the user selects "Thick Line" from the stroke dropdown while an unsupported arrowhead style (Cross, Double Cross, Circle, Double Circle) is active, the arrow style is automatically coerced to its standard thick-supported counterpart (`arrow` or `double_arrow`), allowing the stroke change to succeed.
    - **Arrow Style to Cross/Circle**: If the user selects an unsupported arrowhead style (Cross, Double Cross, Circle, Double Circle) while the line is currently a "Thick Line", the stroke style is automatically coerced to "Solid Line", allowing the arrowhead style change to succeed.
  - **Line Color**: Toggles the active outline on preset stroke colors.
  - **Zap/Flow Animation**: Configures real-time animated flow effects across the path using Mermaid's native v11+ property-based edge animation syntax. When enabled, a deterministic edge ID (e.g. `e_A_B_0@`) is prepended to the connector on the targeted edge line, and a corresponding property declaration `e_A_B_0@{ animate: true }` is cleanly appended to the end of the diagram. When animation is toggled off and the edge uses our deterministic ID pattern, both the property declaration and the prepended ID prefix are automatically removed, restoring the clean diagram syntax. Manual/custom user-defined edge IDs are fully preserved during animation toggling.
    - **Inline `@{...}` shape-source split (CRITICAL)**: When the edge's SOURCE node carries inline shape metadata on the same line (e.g. `A2@{ shape: flip-tri, label: "x" } ==>B`), the edge ID can NOT be placed after the `}` — `A2@{...} e_A2_B_0@==>B` is invalid Mermaid (`Parse error: Expecting 'AMP', got 'LINK_ID'`) and the diagram fails to render, so the animation silently never appears. `updateLinkAnimation` detects an inline `@{...}` shape on the source and SPLITS it: the shape stays on its own node-definition line and the edge ID is placed after the bare source id — `A2@{...}` + newline + `A2 e_A2_B_0@==>B`. Duplicate node-def lines are harmless (Mermaid merges them). Bracket-label sources like `A["x"] e_A_B_0@-->B` are unaffected; only the `@{...}` shape syntax requires the split.
  - **Edit Label Text**: Centers the glassmorphic `<textarea>` overlay directly over the edge label for inline editing.
  - **Delete Edge**: Deletes the connection from the raw Mermaid source. To prevent accidental node deletion, the source and target nodes are preserved as standalone parentless/orphan nodes in the flowchart if they are not defined or referenced elsewhere in the diagram code.
- **Global Edge Curve Config**: Located in the main flowchart top bar toolbar, this allows toggling the global flowchart interpolation/routing curve style (orthogonal step, curve basis, linear straight) for all links in the flowchart, persisting directly inside the diagram config frontmatter block.
- **Two-Way Label Sync**: Double-clicking an edge label, or clicking the pencil button, triggers the dynamic `<InlineTextEditor>` at the exact coordinates of the label. Submitting the text (by pressing Enter or blurring) serializes the edge label back to the Mermaid code in the standard format (e.g. `A -->|New Label| B`) and instantly re-renders the diagram on the canvas.
- **Link Style Preservation & RebuildLinkStyles Bypass**: Styling updates like Line Color and Zap/Flow Animation append `linkStyle` rules to the end of the Mermaid code. Because style modifications do not alter the link structure (no lines added or removed), `rebuildLinkStyles` is bypassed for these operations, passing `updatedCode` directly to `handleCodeChange`. This prevents custom style rules from being lost during compilation rendering.
- **Centralized Connector Matching Pattern**: Standardized and ordered all Mermaid link connectors from longest/most-specific to shortest/least-specific in `CONNECTOR_PATTERN` in `src/lib/diagrams/utils.ts`. This resolves regex prefix conflicts (where shorter subset connectors like `-->` falsely matched inside longer superset connectors like `<-->` or `x--x`). Furthermore, to handle word boundary (`\b`) transitions seamlessly on connectors ending in word characters (such as `--x` or `--o` directly connected to a destination node), we use an elegant lookbehind pattern `(?:\\b|(?<=[xoXO]))${dst}\\b`. This ensures robust arrow type editing, stroke styling, label updating, and styled edge deletion without corrupting the Mermaid syntax.
- **Preset Color Selection Cleanups**: Removed the redundant `'White'` and `'Black'` presets from `PRESET_COLORS` in `src/lib/diagrams/constants.ts` to provide a premium, tailored preset palette for flowchart elements.

## 10. Version History & Rollback

- **Snapshot Source of Truth**: Each diagram document persists a `versionHistory` array in its local JSON file. The editor records the previously saved Mermaid code whenever a real code change is committed through the save path.
- **User Metadata**: History entries can be renamed inline and starred as pinned favorites. These fields live on the same version record and are persisted back through the diagram update route.
- **No Per-Entry Code Preview**: Snapshot rows show the editable name, timestamp, star, and Preview/Rollback actions only. The raw-code `<pre>` snippet that older versions rendered per entry has been removed to keep the list compact; users inspect a version via the read-only Preview canvas instead.
- **Rollback Behavior**: Restoring a version replaces the current code with the selected snapshot and then saves it through the same document update path, which preserves the rollback as a new history entry.
- **Read-Only Preview Workspace**: Opening history now creates a split workspace where the right panel lists snapshots and the left side renders the selected snapshot diagram in a read-only preview canvas. The preview supports pan/zoom/reset controls and is visually marked as non-editable.
- **Preview Interaction Parity**: The history preview canvas mirrors the main canvas interaction model for navigation (`wheelDisabled: true`, `trackPadPanning: enabled`, `limitToBounds: false`) so trackpad panning behaves consistently across both views.
- **Canvas Background Policy**: Diagram render surfaces stay white in both light and dark themes (main editor canvas and history preview canvas) to preserve Mermaid readability and contrast.
- **Pop-out Backdrop Policy**: Pop-out surfaces (dialogs and overlays) use a stronger dimming backdrop in dark mode to preserve depth separation and visual focus (`dark:bg-black/70`).
- **Retention**: Version history is capped at the most recent 100 snapshots so local JSON documents remain predictable while still preserving long-running edit history.

## 11. Testing & Browser Interaction Best Practices

- **Temporary Test Diagrams**: To prevent binding failures, corrupted workspace states, or broken diagrams during interactive browser testing, you MUST always create a new, temporary diagram/flowchart at the start of your test session.
- **Cleanup**: Once your browser testing is completed and verified, you MUST delete or purge the temporary diagram/flowchart to restore the workspace to its clean, original state.
- **Human-Reaction Simulation Protocol (Click/Double-Click Bugs)**:
  - Simulate realistic user pacing, not only synthetic instantaneous sequences: single-click select, then immediate second-node click, then double-click transitions.
  - Validate both behavior and signal: confirm visual state (selection box / inline editor) and diagnostic logs (`[canvas-click]`) for each step.
  - Always compare two paths: clicking label text (`foreignObject`/HTML) vs clicking SVG geometry (`rect`/`path`) because they can dispatch differently.
  - Include negative controls: empty-canvas click and toolbar click to ensure guards (`data-scale-lock`, `data-inline-toolbar`) still suppress unintended transitions.
  - Treat browser dialogs (`beforeunload`) as part of test flow; they can interrupt automation and create false negatives if not resumed.
  - Keep one reproducible script for "human-like" regression: select A, double-click A to edit, immediately double-click B, verify B editor opens and A commit is preserved.

## 12. Global Keyboard Shortcuts

- **Keyboard-Driven Canvas Deletion**: When a diagram node or flowchart edge/line is selected, users can press `Backspace` or `Delete` on their keyboard to instantly delete it from the diagram canvas and Mermaid code.
- **Form/Input and Code Isolation**: The keydown event listener is completely disabled when any input, textarea, contenteditable container, or the Monaco Editor has focus. This prevents elements from being accidentally deleted while typing comments or updating diagram text code.
- **Canvas Focus Blur**: To ensure that selecting canvas elements (which are SVG elements and not focusable by default) immediately enables deletion shortcuts without being blocked by active Monaco editor focus, clicking any canvas element or empty space (inside `handleSvgClick`) programmatically blurs the active text input or editor via `document.activeElement.blur()`. This shifts browser focus away from Monaco/inputs to the document body, activating the deletion listeners safely.

## 13. Exit Confirmation

- **Leave Editor Notice Dialog**: Internal navigation away from the current editor route uses a confirmation dialog before routing, requiring explicit user confirmation (`Leave Editor`) or cancellation (`Stay`).
- **Browser Exit Prompt**: Refreshing or closing the tab while in the editor triggers the browser-native `beforeunload` confirmation prompt **ONLY when there is unsaved work in flight**. `useEditorState` tracks a `hasUnsavedChangesRef` that flips true on every edit and clears only after the debounced auto-save (`DEBOUNCE_MS = 1000`) is confirmed by the server (kept true on save failure). The `beforeunload` handler in `LiveMaidEditor` early-returns (no prompt) when the ref is false, so leaving after the "Saved" state is friction-free; the effective warn window is the ~1 s debounce + the in-flight PUT. This is preferred over an arbitrary "edited within N seconds" timer because it never warns when everything is already persisted and always warns while a save is pending.
- **Browser Back Button Guard**: Pressing the browser back button inside the editor is intercepted and routed through the same leave-editor confirmation dialog before navigation is allowed.

## 14. Dashboard Lazy Loading

- **Pagination Strategy**: The dashboard implements progressive loading of diagram cards using IntersectionObserver API. Initially, 6 diagrams are displayed, with additional batches of 6 loaded as the user scrolls down.
- **State Management**:
  - `displayCount` state tracks the current number of diagrams to display (starts at 6, increments by 6).
  - `sentinelRef` creates a sentinel div at the bottom of the grid that triggers loading when visible.
- **Computed Values**:
  - `filteredDiagrams` uses `useMemo` to filter all diagrams by search query (only recalculates when diagrams or searchQuery changes).
  - `displayedDiagrams` uses `useMemo` to slice filtered diagrams to show only `displayCount` items (optimizes rendering performance).
- **Intersection Observer**: Watches the sentinel div with `threshold: 0.1`. When the sentinel becomes visible and more diagrams exist, `displayCount` is incremented by 6 (capped at total available).
- **Visual Feedback**: A spinning `Loader2` icon displays at the sentinel position when more diagrams are available, providing clear indication that additional content exists below.
- **Search Integration**: When search query changes, filtered results are recalculated and `displayCount` is effectively reset (since new filtered results use the existing displayCount slice). This ensures search works seamlessly with lazy loading.
- **Performance Benefit**: Lazy loading reduces initial page render time and DOM complexity by only rendering visible cards in the viewport, significantly improving dashboard responsiveness with large diagram libraries.

## 15. Sequence Diagram Visual Interactions

- **Double-Click Rename**: Double-clicking a sequence participant (actor) box opens the `InlineTextEditor` overlay positioned at the actor's header box. On submit, `handleEditSubmit` updates the `as {alias}` portion of the participant declaration in the Mermaid code.
- **Logic-Block / Section Label Rename (double-click)**: Double-clicking a logic block's label box renames it inline. The opener label (e.g. the `Retry` in `loop Retry`, rendered by Mermaid as a `.loopText` `[Retry]` box) and section-divider labels (`else`/`and`/`option`, rendered as `.sectionTitle` boxes) are both editable. On submit only the label PORTION of the source line is rewritten (`handleEditSubmit` `SEQ_BLK_` branch: `/^(\s*)(loop|alt|opt|par|critical|break|else|and|option)\b[ \t]*(.*)$/` → keep indent + keyword, replace the rest; an empty new label collapses to the bare keyword). Implementation details:
  - **DOM→source mapping is by Y-sort, NOT DOM order (CRITICAL)**: Mermaid does NOT paint `.loopText`/`.sectionTitle` in source order — nested/inner blocks paint their labels FIRST (verified: source openers OUTER,INNER,P-A,LAST paint as INNER,P-A,OUTER,LAST). But a block's label always sits at the TOP of its box and section dividers never vertically cross, so **sorting the label elements by their on-screen `getBoundingClientRect().top` reproduces SOURCE order exactly**. `resolveSequenceBlockLabelTarget(clickedEl)` (in `useCanvasInteraction.ts`) Y-sorts all `.loopText` (resp. `.sectionTitle`) and indexes into the parser's source-ordered openers (resp. else/and/option dividers from `getSequenceBlockEntries().sections`), returning the absolute source `lineIndex`. The node id is `SEQ_BLK_<lineIndex>`.
  - **`rect` excluded**: `rect` highlights render NO `.loopText` (only a colored box, no text label), so the opener list filters `type !== 'rect'` to keep the Y-sorted ↔ source-order map 1:1. A label-less `loop`/`opt`/etc. STILL renders a `.loopText` (a zero-width space), so it stays in the map and is renamable (adds a label).
  - **Editor wiring**: handled at the TOP of `handleEditClick` (before the generic `getClickedNode` path so it never falls through to flowchart-node rename). It positions the shared `InlineTextEditor` over the clicked label's rect, sets `selectedNodeId = SEQ_BLK_<line>`, seeds `editingText` from the source label, and supports the same cross-element/commit transition as message/note editing. **`recalculateSelection` early-returns for `SEQ_BLK_`** — block labels have no persistent SVG element to re-resolve, so without that guard the "couldn't find element" branch would clear the selection box ~50ms after open and the editor would vanish mid-edit. Selection is cleared on submit.
- **Highlight (`rect`) Recolor (double-click)**: Double-clicking a `rect` highlight's colored background opens a small color popover (8 preset swatches + a native "Custom…" color input). Choosing a color rewrites ONLY the color argument after the `rect` keyword (`handleRecolorSequenceHighlight` in LiveMaidEditor: `/^(\s*)rect\b.*$/` → `${indent}rect ${color}`, custom hex converted to `rgb(r, g, b)`), preserving indentation; routes through `handleCodeChange` (single undo). Highlights carry no text label, so this is their analogue of the block-label rename. Implementation details:
  - **DETECTION MUST run through `handleEditClick`, NOT EditorCanvas's React `onDoubleClick` (CRITICAL)**: `react-zoom-pan-pinch` swallows the synthetic `dblclick` on SVG `<rect>` elements (the `TransformWrapper` intercepts it at its own capture listener even with `doubleClick.disabled`), so the canvas `<div onDoubleClick>` NEVER fires for a rect background — an early implementation there silently did nothing on every clean load (it only appeared to work under stale Fast-Refresh closures). The reliable path is the hook's document-level **capture-phase `dblclick`** listener (`handleNativeDblClick`) which drives `handleEditClick`; the rect recolor is therefore detected at the TOP of `handleEditClick` (same place as block-label rename and before `getClickedNode`). Do NOT move highlight detection back onto the React `onDoubleClick`.
  - **DOM→source mapping by Y-sort**: highlights render as `<rect class="rect" fill="rgb(...)">`; like block labels they are NOT painted in source order, but their TOP edges are strictly ordered, so `resolveSequenceHighlightTarget(clientX, clientY)` Y-sorts the `rect.rect` (rgb-fill) elements and indexes into the source-ordered `rect` blocks from `getSequenceBlockEntries`, returning `{ lineIndex, color }`. The hit rect itself is found via `document.elementsFromPoint` (class `rect` + rgb-ish `fill`).

So after the splice, `handleReorderSequenceItem` runs `pruneEmptySequenceBlocks(lines)` (module-level in LiveMaidEditor): a stack-based pass that drops any block whose body has NO real content (only section dividers `else`/`and`/`option`), removing the opener line, its section-divider lines, and the matching `end`. Content propagates to parents (a parent containing only empty children is itself pruned, so one pass handles arbitrary nesting). ANY non-empty, non-structural line counts as content, so blocks that still hold something are never touched. Verified: dragging the lone message out of a `rect` (its only child) auto-removes the now-empty `rect … end` and the diagram keeps rendering instead of crashing. Do NOT remove this prune — naive line-splice reordering across block boundaries is otherwise unrenderable.
  - **Note hover MUST use the onMouseOver path, not just mousemove (CRITICAL)**: Message hover works via BOTH `handleSequenceHoverOver` (React `onMouseOver`) and the RAF-throttled mousemove inner handler. Note hover originally only lived in the mousemove inner handler — which in practice does not reliably deliver the sequence branch (message hover visibly works purely through `onMouseOver`), so the note grab overlay never appeared. Fix: `updateSequenceNoteHover(clientX, clientY)` is called from `handleSequenceHoverOver`/`handleSequenceHoverOut`, doing a viewport-coordinate hit-test against `rect.note` boxes (coordinate-based, NOT `e.target`-based) so it stays stable even when the note's pointer-events:auto grab overlay covers the note and changes `e.target`. Do NOT rely solely on the mousemove path for note hover.
  - **Click/double-click handled on MOUSEUP, not the `click` event (CRITICAL)**: When the overlay receives a real `mousedown`, the resulting state churn (hover update + selection mounting the second handle) re-renders and REPLACES the overlay DOM node between `mousedown` and `mouseup`, so the browser never fires a native `click` on a single stable node (confirmed: `mousedown`+`mouseup` fire but no `click`). Therefore select-vs-edit is resolved inside `startSeqReorderDrag`'s window `mouseup` (`onUp`) handler when no drag occurred: it calls `onHoveredSequenceMessageClick(fromIndex)` to select, or `onHoveredSequenceMessageDoubleClick(fromIndex)` to edit. Double-click is detected by TIMING (`seqLastClickRef`): two no-drag mouseups on the same message index within 350ms ⇒ edit. This is robust against the DOM node replacement that breaks both native `click` and `e.detail`. The hover grab overlay renders for the hovered message REGARDLESS of selection so EVERY message's mousedown registers this `onUp` path (only the VISIBLE hover ring keeps the `!selectedNodeId?.startsWith('SEQ_MSG_')` condition to avoid a double ring). Do NOT move this logic back onto `onClick`/`onDoubleClick`.

Do NOT remove this guard.
  - **Viewport-space visuals**: All drag geometry (drop-zone bands + cursor ghost) is computed in viewport space relative to `canvasShellRef` from live DOM rects (`.messageText` centers for slot Ys, `line.actor-line` extent for horizontal span) and rendered OUTSIDE `TransformWrapper` — the same robustness pattern as `seqDragIndicator`. Panning is disabled during the drag so coordinates never shift.
  - **Slot model**: N messages → slots `0..N` (0 above first, `k` between `k-1`/`k`, `N` below last). Drop zones render for every slot EXCEPT the dragged message's own gaps (`from` and `from+1`). The nearest slot to the cursor highlights (solid indigo); others are dashed hatched bands. Drop is valid only when the cursor is within `[slotY(0)−28, slotY(N)+28]` and near the diagram width; otherwise the drop cancels and the message snaps back (no code mutation).
  - **Strict hitbox drop detection (cancel on invalid drop, CRITICAL)**: A reorder commits ONLY when the cursor falls INSIDE a drop zone's bounding box — `findTarget` tests explicit intersection `cursorY ∈ [s.y − (s.h/2 + 6), s.y + (s.h/2 + 6)]` AND `cursorX ∈ [left − 24, left + width + 24]`, returning `null` (→ abort/snap-back) when the drop lands in the dead space between zones, in the dragged message's own excluded gaps, or off to the side. The SAME `findTarget` drives both the live preview highlight and the commit, so a highlighted zone honestly means "drop here will land"; no highlight means the drop will cancel.
  - **CRITICAL — interstitial Y from message BANDS, not text midpoints**: Each message occupies a vertical BAND = its `.messageText` label UNION its arrow line (`messageLine*`). In Mermaid the arrow line sits BELOW the text label, so the empty gap between two messages is `band[k−1].bottom … band[k].top` — NOT the midpoint between text centers (that midpoint lands directly on the upper message's connection line). The slot Y is the center of that empty gap, and each zone's HEIGHT is clamped to `emptyGap * 0.7` (5–14px) so it never touches a line/label. Verified: 0 zones overlap any text center or line center (flat arrows and self-loop arcs included).

Routes through `handleCodeChange`, so undo/redo (Monaco) and autonumber behave exactly like every other canvas mutation. Selection is cleared after a successful move. Implementation:
  - **Endpoint geometry (`getSequenceMessageEndpointGeometry(idx)` in `useCanvasInteraction.ts`)**: Returns `{ from, to, isSelf, source:{x,y}, target:{x,y}, lifelines:[{actorId,x}] }` in **canvas coordinates** (pre-transform). Combined with the centered `top: pt.y` placement, the bar always straddles its own endpoint symmetrically and never drifts onto a neighboring row. Verified on `test-seq-diagram`: bars centered on the endpoint line (handle cy ≈ line y) at scale 0.5×, 1×, and 4.7×, staying lifeline-aligned throughout. Do NOT use plain `data-scale-lock` or an unclamped `1/scale` here, or the bars balloon at min zoom.

  - **Commit (`handleChangeSequenceMessageEndpoint(endpoint, newActorId)` in LiveMaidEditor)**: Splits the message line at the first `:`, matches the pre-colon segment with `/^(\s*)(\S+?)(\s*)(<<-->>|<<->>|-->>|--x|--\)|-->|->>|-x|-\)|->)(\s*)(\S+)(\s*)$/`, and swaps ONLY the sender or receiver slot — operator, the other actor, label (everything from `:` on), and all spacing are untouched. Self vs cross is implicit: when sender === receiver the resulting `A->>A: msg` is a valid Mermaid self-message.

A greedy sender swallows the leading dash of a double-dash operator — `B-->>A` parses as sender `B-` + op `-->>` (the first successful backtrack position), breaking lifeline resolution and the endpoint mutation for ALL dotted/cross messages (`-->>`, `-->`, `--x`, `--)`). Single-dash ops (`->>`, `->`, `-x`, `-)`) happen to be safe because the intermediate backtrack positions (`>>`, `>`) are not valid operators. ## 16. Demo Mode

- **Activation**: Set a single `DEMO_MODE=true` environment variable. Typically done via Docker Compose (see `docker-compose.yml`, the `livemaid-demo` service) or a host platform's service variables (e.g. Railway).
- **Runtime-driven (NOT build-time)**: `DEMO_MODE` is a server-side var read at **request time**, never baked into the build. The dashboard (`src/app/page.tsx`) and editor (`src/app/editor/[id]/page.tsx`) server components call `await connection()` (from `next/server`) before reading `process.env.DEMO_MODE`, which opts them out of static prerendering. The resolved boolean is passed down as the `isDemo` **prop** to the client components. **Do NOT reintroduce a `NEXT_PUBLIC_DEMO_MODE` flag** — `NEXT_PUBLIC_*` vars are inlined into the client bundle at build time and cannot be toggled by a runtime env var (this broke the demo banner/buttons on Railway, which sets env vars only at container start). The `connection()` call is required: without it, `/` is statically prerendered and `DEMO_MODE` would be frozen at build time.
- **Read-Only Storage**: When `DEMO_MODE=true`, the server reads diagram data from the `./demo/` directory instead of `./data/`. The `saveDiagram` and `deleteDiagram` functions in `src/lib/api/storage.ts` are no-ops.
- **Disabled Write APIs**: The `POST /api/diagrams` (create) and `DELETE /api/diagrams/[id]` routes return HTTP 403. The `PUT /api/diagrams/[id]` route silently returns the existing document unchanged instead of saving.
- **Client-Side Guard**: `useEditorState(documentId, isDemo)` receives `isDemo` as a parameter (from the editor page's runtime `DEMO_MODE` read, via `LiveMaidEditor`) and skips the debounced auto-save entirely when true.
- **Demo Banner**: A persistent amber `DemoBanner` component (at `src/components/DemoBanner.tsx`) is rendered below the nav/header on both the Dashboard and the Editor. It clearly states that all changes are temporary and won't be saved.
- **Hidden Write Actions**: In demo mode, the "New Diagram" and "Create Diagram" buttons are hidden on the Dashboard. The rename and delete icon buttons on `DiagramCard` are also hidden. In the editor header, the "New Diagram", "Duplicate", and "Rename" menu items are removed, and the save status indicator shows "Read Only" instead of "Saved"/"Saving...".
- **Demo Content**: Populate the `./demo/` folder with pre-seeded `.json` diagram files (same format as `./data/`) that showcase the app's capabilities.

## 18. Inline Toolbar Reliability (Sequence / Edge / Node Manipulation Toolbars)

All three floating manipulation toolbars (`SequenceManipulationToolbar`, `EdgeManipulationToolbar`, `NodeManipulationToolbar`) are nested inside the selection box and marked with `data-inline-toolbar` + `data-scale-lock`, with a transparent padding shield and `stopPropagation` on their own pointer events. The following guards keep them robust against the canvas hit-testing underneath:

- **Hover suppression over the toolbar (both hover paths)**: A floating-UI guard — `document.elementsFromPoint(clientX, clientY).some(el => el.closest('[data-inline-toolbar]') || el.closest('[data-scale-lock]') || el.closest('[data-scale-lock-border]'))` — runs at the top of BOTH sequence hover paths (`handleSequenceHoverOver` for `onMouseOver`, and the RAF-throttled `_handleMouseMoveInner` for `onMouseMove`). When the cursor is over a toolbar it clears all sequence hover state and returns, so the hover grab overlay of the message _behind_ the toolbar never renders on top of it (which previously stole the press and reselected the wrong message). Both paths need the guard because `onMouseMove` keeps firing while the cursor sits still over the toolbar.
- **Stacking order**: The selection-box border `<div>` that nests the toolbar is `z-[22]`, above the `z-[21]` sequence hover grab overlays, so the toolbar paints and hit-tests above neighbouring-message overlays.
- **Dropdown toggles fire on capture-phase mousedown**: The custom Message Type / Move dropdowns (plain `useState`, not Radix) toggle on `onMouseDownCapture`, not `onClick`. The toolbar container has a native bubble-phase `stopPropagation` listener (added via `addEventListener` in a `useEffect`) to block canvas leakage; React delegates synthetic handlers at the root, so a bubble-phase React `onPointerDown`/`onMouseDown` is killed by that native listener before it reaches the root. Capture-phase handlers fire root→target BEFORE any bubble listener, so the dropdown opens reliably even when a transient re-render moves the toolbar so the browser fires no native `click`. (A no-op `onClick={e => e.stopPropagation()}` remains to avoid a double-toggle.)
- **Never render the flowchart Node toolbar on a sequence diagram**: The toolbar ternary in `EditorCanvas` (`isEdgeId → Edge`, `SEQ_* → Sequence`, else `Node`) has a defensive `currentType === 'sequence' ? null :` branch before the `NodeManipulationToolbar` fallback. This prevents the wrong (flowchart) style bar from flashing during the brief window where `onDeselect` has cleared `selectedNodeId` (a separate state setter) while `selectionBox` still lingers — e.g. during a zoom/deselect transition (all zoom controls and `onZoomStart`/`onPinchStart` call `onDeselect`).

## 19. Canvas-to-Code Highlighting (Epic 4.1)

Selecting an element on the canvas highlights its source line(s) in the Monaco code panel and scrolls them into view. This is a one-way, read-only sync (canvas selection → code decoration); it never mutates the code, so it is fully active in demo mode too (AC 4.1.3).

- **Line-range resolution (`highlightRange` memo in `LiveMaidEditor`)**: A `useMemo` keyed on `selectedNodeId` + `code` maps the selection to a 0-indexed inclusive `{ startLine, endLine } | null`:
  - `SEQ_MSG_<i>` → `getSequenceMessageEntries(code)[i].index`
  - `SEQ_NOTE_<i>` → `getSequenceNoteEntries(code)[i].index`
  - `SEQ_BLOCK_<startLine>` → matching `getSequenceBlockEntries` entry's `startLine..endLine` (opener..`end`, the only multi-line highlight)
  - `SEQ_ACTOR_<id>` → `findSequenceParticipantLine` (declaration); falls back to the first message line referencing the actor when it is implicit (never declared)
  - edge ids (`isEdgeId`) → `findFlowchartEdgeLine(code, src, dst, occurrenceIndex)`
  - plain flowchart node id → `findFlowchartNodeLine` (prefers the declaration line `A[...]`/`A@{...}`, else first reference)
  - `null` selection → `null` range (clears the decoration — AC 4.1.2)
- **Pure helpers live in `src/lib/diagrams/selectionLineMap.ts`** (`findFlowchartNodeLine`, `findFlowchartEdgeLine`, `findSequenceParticipantLine`). They return -1 for "no confident match" so callers render no highlight rather than guess. **Pitfall:** when building character classes from a shared id-charset string, the charset must be the class _body_ (`A-Za-z0-9_-`), not a bracketed class (`[A-Za-z0-9_-]`) — embedding the latter inside `[^…]` produces a broken nested class that silently matches nothing.
- **Decoration + scroll (`EditorCodePanel`)**: The panel captures the real Monaco `editor` + `monaco` namespace in `onMount` (still calling the parent's `handleEditorDidMount` for undo/redo), then in a `useEffect` on `highlightRange` applies a single whole-line decoration via a `createDecorationsCollection()` (classes `canvas-code-highlight-line` + `canvas-code-highlight-gutter`, styled in `globals.css`, theme-agnostic) and calls `revealLineInCenter(startLine + 1)` (Monaco is 1-indexed). A null range calls `.clear()`. Mount also applies any range that was already pending.
- **Testing note**: Playwright/CDP `mouse.down()` does NOT register as a canvas selection here (react-zoom-pan-pinch swallows the synthetic input), so the document-level `mousedown`-capture selection listener never fires. Dispatching a native `new MouseEvent('mousedown', { bubbles: true, clientX, clientY })` on the element at a point found via `elementsFromPoint` DOES trigger the real handler chain and is the reliable way to exercise selection-driven features in automated tests.

## 20. Class Diagrams (modular plugin)

Class diagrams are implemented as a fully self-contained plugin (`src/lib/diagrams/classDiagram.tsx`) registered under the key `classDiagram` in `registry.ts`. The only edits outside the plugin are: the registry entry, the Dashboard create-dialog type picker, the EditorCanvas guards + panel render, and the LiveMaidEditor wiring for the property panel. Existing diagram types are untouched (verified: flowchart + sequence selection/toolbars unaffected).

- **Type detection & creation**: `determineDiagramType` returns `"classDiagram"` for class-diagram code (its generic first-keyword branch), so the plugin registers under that exact key. The Dashboard "Create New Diagram" dialog has a Flowchart/Sequence/Class **type picker** and sends `code: DiagramRegistry[type].defaultCode` in the POST body. **CRITICAL — no `"use client"` in plugin files**: `classDiagram.tsx` (like `flowchart.tsx`) must NOT carry the `"use client"` directive. The `POST /api/diagrams` route imports the registry server-side to read `defaultCode`; a `"use client"` module's exports become client references whose `.defaultCode` is `undefined` server-side, persisting a diagram with empty code. (Sending the default code from the client sidesteps this for all types, including `sequence.tsx` which does carry `"use client"`.) **The same constraint forbids client-only IMPORTS at the plugin's module top** — e.g. `import { useState } from "react"` or any `@/components/ui/*` component that transitively uses hooks. Turbopack treats the whole module as a Client Component and the server-side `route.ts → registry.ts → classDiagram.tsx` import chain 500s with _"You're importing a module that depends on `useState` into a React Server Component module."_ This is why the Title-removal confirmation does NOT import an `AlertDialog` + `useState` into the plugin. Instead the client editor (`LiveMaidEditor`) implements a promise-based **`requestConfirm(opts)`** provider — it owns the AlertDialog state + a resolver ref, renders one shared `<AlertDialog>`, and passes `requestConfirm` down through `EditorContext` to the plugin toolbar. The plugin just `await requestConfirm({ title, description, confirmLabel, destructive })` (falling back to `window.confirm` if the callback is absent), keeping `classDiagram.tsx` free of any client-only imports.
- **Toolbar (`ClassDiagramToolbar`)**: two inline pill toggles first — **Hide Empty Members** (driving `hideEmptyMembersBox`) and **Title** (next to it, same uppercase-label + pill-switch markup as the sequence Auto Number toggle; ON upserts a `title: Diagram Title` frontmatter key via `upsertClassTitle`, OFF first asks for confirmation — turning the toggle OFF would drop the user-entered title text, so `handleToggleTitle` (now `async`) calls the injected `requestConfirm({ title: "Remove diagram title?", description, confirmLabel: "Remove title", destructive: true })` and only `removeClassTitle`s on accept; derived state = `getClassTitle(code)` non-empty) — then Add Class / Add Note buttons, and a layout-direction dropdown (mirrors the flowchart `direction` control — both use a labelled **“Direction”** button with a `Workflow` icon, NOT an icon-only chevron — but writes a `direction TB|BT|LR|RL` **statement line** under `classDiagram`, not a header suffix). Add Class inserts `class UntitledClass{N} {}` with a collision-free id; Add Note appends `note "This is a sample note"`. (Title is a toggle, no longer a button; the diagram title TEXT is still editable by double-clicking it on the canvas.)
- **Frontmatter helpers (in the plugin)**: `title:` lives in the YAML frontmatter and is always written **after** any `config:` block so the config-anchored global helpers keep matching. `hideEmptyMembersBox` is a **nested** `config.class.hideEmptyMembersBox` flag (NOT a top-level config key), so it has a dedicated line-based writer (`setHideEmptyMembersBox`) that keeps `config:` first.
- **Hardened global frontmatter helpers (regression fix, `utils.ts`)**: `updateMermaidConfigProperty` (theme) and `updateMermaidFontFamily` (font) previously captured everything between `config:` and the closing `---`, so a trailing top-level key such as the new `title:` was swallowed into the config block and orphaned by an appended mapping entry → invalid YAML (`bad indentation of a mapping entry`). Both now capture **only the indented children** of `config:` and inject into an existing frontmatter block instead of prepending a duplicate. Verified: changing theme/font on a titled class diagram stays valid; flowchart/sequence theme/font unchanged.
- **Contextual Property Panel (the "better approach", replaces a blocking modal)**: **Double-clicking** a class node opens a right-sidebar `ClassPropertyPanel` (`top-20 right-3`, outside the `TransformWrapper`; a single click only selects the node, it does NOT open the panel — double-click is detected by timing, see the Title & Note entry below). The panel is always dark (`bg-[#100f1b]`, white-alpha borders) per the DESIGN.md contrast-inversion rule. The top holds two-way-bound **Class name** + **Annotation** inputs; below them a **structured table grid** (headers `Class Property` | `Value`) groups members by section — **Attributes** and **Methods** in the left column, each member rendered as its own borderless monospace input row in the right column. Each row has, at the back: a **drag handle (the dot)** to reorder rows within its section (HTML5 DnD; the order syncs to code + canvas), and a hover-revealed **delete button (trash)** to remove that member (a section keeps ≥1 blank row). Members are stored as `string[]` per section. **Enter** on a row inserts a blank row below and focuses it; **Backspace** on an already-empty row removes it. The flowchart `NodeManipulationToolbar` and the Quick-Add `+` button are suppressed for class diagrams (`currentType === "sequence" || currentType === "classDiagram" ? null :` and `currentType !== "classDiagram"` guards in `EditorCanvas`). Rows/annotation commit on a 400 ms debounce (cleaned: trimmed + empties filtered, so blank rows never emit malformed Mermaid); reorder/delete commit immediately; the class name commits on blur/Enter and re-binds the panel to the new name. Row focus across add/remove is managed explicitly via per-section `inputRefs` + a `pendingFocus` ref applied in a `focusTick`-keyed effect (index keys are intentional).
- **Title & Note inline editing (`ClassTextEditor`)**: **Double-clicking** the diagram **title** (`text.classDiagramTitleText`; CSS `cursor: pointer` over it) or a **note** (`g.node` with an id ending `-note<N>`) opens a small viewport-fixed text editor positioned over the element (seeded from the code). **Enter** or **clicking outside** commits; **Escape** cancels. Title writes via `upsertClassTitle`/`removeClassTitle` (empty ⇒ remove); the Nth note writes via `updateClassNoteByIndex` (preserves the `note`/`note for X` head, only the quoted text changes). Routing lives in a `LiveMaidEditor` document-capture listener (gated to `classDiagram`; resolves the real target via `elementsFromPoint`) which ALSO handles the class-node→panel open above. **CRITICAL — double-click is detected by TIMING, NOT the native `dblclick` event**: the first click selects the node and mounts a selection overlay, so the second click lands on a different target and the browser dispatches NO native `dblclick` (verified: two real clicks never fired it; only a synthetic `dblclick` did). The listener therefore tracks two `mousedown`s at (nearly) the same point within 400 ms and runs `elementsFromPoint` (which sees through overlay divs to the SVG) to route title/note/class. Do NOT revert to a `dblclick` listener. **CRITICAL — outside-click commit, not blur**: the canvas pan handler calls `preventDefault` on `mousedown`, which suppresses the textarea's default blur, so `ClassTextEditor` registers its OWN capture-phase `document` `mousedown` listener (reading the latest value from a ref) to commit on any outside press. Do NOT rely on `onBlur` alone.
- **Parsing/serialization**: `parseClassByName(code, name)` gathers members from BOTH the brace form (`class Foo { ... }`) and the colon form (`Foo : +member`), plus annotations declared inline / `<<x>> Foo` / nested. `applyClassEdits(code, name, edits)` re-serialises into the canonical brace form, removes now-redundant colon lines, and propagates a rename to relationship lines via a whole-word swap. The class name is recovered from the SVG node id via `classNameFromSvgId` (`…-classId-<Name>-<n>` → `<Name>`, greedy to support dashed names).
- **Sticky selection (CRITICAL)**: The interaction hook's `recalculateSelection` clears the ENTIRE selection (incl. `selectedNodeId`) whenever it cannot re-resolve a node after a re-render — which happens for class nodes on **every member edit** (Mermaid re-renders with a new `mermaid-svg-<ts>` prefix and the round-trip match fails). Deriving the panel directly from the live selection therefore closes it mid-edit. Instead `selectedClassName` is **sticky state** in `LiveMaidEditor`, set by the double-click listener (NOT by `selectedSvgId`), and closed only by: the panel's X button, a rename re-bind, or a **capture-phase `document` `mousedown` listener** that fires when the click is neither inside `[data-class-property-panel]`, inside the Monaco code editor (`.monaco-editor`), nor on a `g.node[id*="classId-"]`. The `.monaco-editor` exemption is what lets the grid **live-update while you edit the `class {}` block in the code panel** (the panel must stay open for code → grid sync to be visible). Do NOT revert to deriving the panel from the live selection.
- **Backspace/Delete safety**: With a class selected, the global delete handler resolves `handleDeleteNode` against the (flowchart-style) selected id, which does not match the `class Foo {}` source, so it is a safe no-op — pressing Delete on a class does not corrupt the code.
- **Global parity (Epic 1.2)**: Undo/redo (toolbar buttons + Cmd/Ctrl+Z), pan/zoom (shared `TransformWrapper`, 1:1 button), and copy/paste shortcuts all work on class diagrams because every mutation routes through `handleCodeChange` (single Monaco transaction). **Canvas→code highlight (Epic 4.1)** also covers class diagrams: the `highlightRange` memo in `LiveMaidEditor` maps the selected element to its source line. CRITICAL: a class node / note is selected on SINGLE-click via `selectedSvgId` (NOT only the double-click `selectedClassName`), so the memo resolves class/note from `selectedSvgId` too — a `…-note<N>` id → that note's line via `getClassNotes`, else `classNameFromSvgId(selectedSvgId)` → its `class X` line via `findClassDefinitionLine`; it still falls back to the sticky `selectedClassName` (double-click). A relationship edge (`CLASS_EDGE_<dataId>`) → its relationship line via `classRelationshipFromEdgeDataId(...).lineIndex`. `selectedSvgId` MUST be in the memo deps. ALL diagram types must keep feeding this memo (sequence/flowchart branches already do) so the code panel lights up + scrolls to the selected element.
- **Single-click toolbar (delete) — `ClassNodeToolbar`**: single-clicking a class node or a note also floats a small inline bar ABOVE the selection box with a **Delete** action (the `+` connect button sits below; the property panel for richer class editing still opens on double-click). It renders in the `EditorCanvas` toolbar ternary via a `currentType === "classDiagram" && (connectSourceClass || connectSourceNote !== null)` branch (placed before the `classDiagram ? null` fallback). Delete routes through `LiveMaidEditor` (`handleDeleteClassNode` / `handleDeleteClassNote`) → `deleteClassByName` (removes the brace block / decl + colon-form members + annotation + ALL relationship lines referencing it + `note for <Class>` attachments) or `deleteClassNoteByIndex` (removes the Nth note in source order) → `handleCodeChange` (single undo), then deselects. Same scale-locked / `data-inline-toolbar` chrome as the other inline toolbars.
- **Connection drag — link classes & notes (the purple +)**: Single-clicking a class node selects it and surfaces a purple `+` below the selection box (`.class-connect-btn`, scale-locked, crosshair cursor; `connectSourceClass` is derived from `selectedSvgId` via `classNameFromSvgId`, NOT the double-click-only property panel). Dragging the `+` is a **fully isolated** drag (own `window` `mousemove`/`mouseup` listeners + preview SVG outside `TransformWrapper` in `canvasShellRef` shell space — the same pattern as the sequence endpoint drag, NOT the shared flowchart `connectionState`). The drop target is resolved with `document.elementsFromPoint`:
  - **another class** → opens the `ClassConnectMenu` relationship picker (8 UML types from `CLASS_RELATIONSHIP_TYPES`); choosing one appends `source <op> target` via `addClassRelationship`.
  - **a note** (`g.node` id `…-note<N>`) → links it to the source class immediately (`note "x"` → `note for <source> "x"`) via `setClassNoteTarget`.
  - **empty canvas / a no-drag click on the +** → opens the `ClassConnectMenu` create chip: **New class** (creates `class UntitledClassN {}` + `source --> UntitledClassN` via `addClassWithRelationship` with a DEFAULT association — the user no longer picks a connection type up front; they can change it later via the edge toolbar) or **New note** (`appendClassNoteForClass` → `note for <source> "This is a sample note"`).
    All four commit handlers live in `LiveMaidEditor` (`handleAddClassRelationship` / `handleLinkNoteToClass` / `handleCreateClassLinked` / `handleCreateNoteForClass`) and route through `handleCodeChange` (single undo). The `+` is added to `panning.excluded` and `classConnecting` to `panning.disabled`; the LiveMaidEditor double-click router bails on `.class-connect-btn` / `[data-class-connect-menu]` so a press there never opens the panel. **Reverse gesture (note → class)**: single-clicking a note also surfaces the `+` (`connectSourceNote`, derived from a `…-note<N>` `selectedSvgId`); dragging it onto a class attaches the note (`setClassNoteTarget` → `note for <Class>`). `startClassConnectDrag` takes a `{kind:'class'|'note'}` source: a note source only accepts a class target (note→note / note→empty / a no-drag click are silent no-ops, since notes have no create/relationship flow). Double-clicking the note still opens its inline text editor (the `+` press is drag-only). **Testing note**: the class/note `+` drag is Playwright-testable (window listeners) whereas the flowchart `+` drag is NOT (it uses react-zoom-pan-pinch React `onMouseMove`/`onMouseUp` props which synthetic mouse can't drive — verify the flowchart `+` via its click-to-add path instead).
- **Relationship & Cardinality management — the edge toolbar (`ClassEdgeToolbar`)**: Clicking a relationship line **selects the edge** and floats a **menu-first** toolbar above it. The class-edge SVG plumbing (verified live, Mermaid 11.15): a relationship renders as `<path class="… relation" id="…-id_<Src>_<Dst>_<N>" data-id="id_<Src>_<Dst>_<N>">` inside `g.edgePaths`; **`N` is a GLOBAL 1-based counter incremented once per relationship across the WHOLE diagram in code order (NOT per-`(source,target)` pair)** — e.g. `A <--> B`, `A <|-- C`, `A -- D` → `…_1`, `…_2`, `…_3`; `getClassRelationships` therefore assigns a single running counter (an earlier per-pair counter left every edge after the first of each distinct pair unselectable, since it computed the wrong expected id), and `data-id` is stable across re-renders (the timestamped `id` is not). NOTE: a class diagram ALSO renders note↔class attachment edges as `path.relation` but with `data-id="edgeNote<N>"` (mapping 1:1 to note DOM node `…-note<N>`, whose index == `getClassNotes` order) — these are NOT UML relationships and are handled separately (see below). To make the thin line clickable, `useEditorState.addSvgInteractionHelpers` clones each `path.relation` into a **50px** transparent `path.class-relation-hit-target` (drops `id` + arrow markers, **removes the `relation` class** so `path.relation` / `path.relation[data-id]` queries stay unambiguous, **AND removes Mermaid's `edge-pattern-dashed`/`edge-pattern-dotted` classes + forces `stroke-dasharray: none !important`** so the hit-target is a SOLID continuous stroke — otherwise a dashed/dotted relationship's hit-target inherits the dash pattern and clicks fall through the GAPS between dashes, making the edge nearly unselectable (the "dashed connection can't be selected" bug), keeps `data-id`). The visible line also gets a `cursor:pointer` + indigo (`#6366f1`) hover highlight via `globals.css` (`path.class-relation-hit-target:hover + path.relation`, adjacent-sibling since the hit-target is inserted immediately before the real path). Selection is wired through the existing hook: `getClickedNode` adds a `.relation` / `.class-relation-hit-target` branch that surfaces `CLASS_EDGE_<dataId>` ONLY when `data-id` starts with `id_` (a note edge `edgeNote<N>` is deliberately NOT selected — it has no type/cardinality, so the toolbar would be empty); the id is kept **verbatim** (`normalizeId` early-returns for it and the `cleanId` line bypasses normalization so the trailing `_<N>` survives); `recalculateSelection` re-resolves it via `path.relation[data-id="…"]`; `class-relation-hit-target` is in `panning.excluded`. The `EditorCanvas` toolbar ternary branches on `selectedNodeId.startsWith("CLASS_EDGE_")` **before** `isEdgeId` so class edges never get the flowchart edge toolbar (`isEdgeId` is deliberately NOT extended). The toolbar is a **two-row compact bar** (`min-w-[16rem] max-w-[22rem]`): **row 1** is the `Source → Target` indicator (both names `truncate` with ellipsis when too long; the `→` stays `shrink-0`), **row 2** is the controls — a **Relationship** trigger, a **Cardinality** trigger, and a **Delete** button. Each trigger toggles its own popover panel that opens **UPWARD** (`bottom-full mb-2`) — the bar floats above the edge via `translateY(-100%)`, so a downward panel would cover the selected line; opening upward keeps the connection visible (capture-phase `onMouseDownCapture` toggle for reliability; outside-click closes; styled with our own theme tokens — NOT a copied platform look). The panels:
  - **Relationship panel**: a **Line** segmented control (solid `--` / dashed `..`) and **always-visible Source end / Target end** marker pickers. There is deliberately NO preset-type grid, NO label field, and NO two-way toggle in the panel — the two end-marker pickers (none/arrow/triangle/diamondFilled/diamondHollow) plus the line style **compose any of the eight UML relationships AND every bidirectional form directly** (e.g. source=none+target=triangle ⇒ `<|--` inheritance, both triangles ⇒ `<|--|>`), so neither a preset grid nor a two-way shortcut is needed; the relationship `: label` is edited by **double-clicking the connection** (see below). The operator model decomposes any operator into `{sourceMarker, lineStyle, targetMarker}` via `parseClassRelationshipOperator` and recomposes with `buildClassRelationshipOperator` (`CLASS_END_MARKERS`: none/arrow/triangle/diamondFilled/diamondHollow, with left/right tokens) — this round-trips ALL eight presets AND every bidirectional form (`<|--|>`, `*--*`, `o--o`, `<-->`, …). Picking a line style / marker rewrites the operator **in place** via `updateClassRelationshipOperator`, preserving cardinality + label.
  - **Cardinality panel**: per-end (**Source** / **Target**) sections, each laying out the 7 preset chips (`—`, `1`, `0..1`, `*`, `1..*`, `0..*`, `n`) + a free-type **custom input** (last cell) in a **4-column grid = two rows** (the popover is fixed `w-64` so the columns stay compact; the input is `w-full text-center` with a `type…` placeholder). The custom input is the `CustomCardInput` sub-component — own draft, commits on Enter / blur, reverts on Escape, remounted per edge+end via `key`, highlighted active when the current value isn't a preset. There is no longer a separate Custom… modal. Both presets and the input write via `setClassRelationshipCardinality` (empty string removes that end's `"card"`), producing `A "c1" <op> "c2" B`.
  - A **Delete** button removes the line (`deleteClassRelationship`) and deselects. All commits resolve the selected edge back to `{source,target,occurrence}` via `classRelationshipFromEdgeDataId(code, dataId)` then route through `handleCodeChange` (single undo). The pure helpers (`parse`/`build` operator, `getClassRelationships`, `classRelationshipFromEdgeDataId`, `updateClassRelationshipOperator`, `setClassRelationshipCardinality`, `setClassRelationshipLabel`, `deleteClassRelationship`) are unit-verified (31/31). Verified end-to-end in browser: select → menu trigger opens panel → change type (`<|--`→`*--`) → two-way (`*--*`) → cardinality presets → custom dialog (`2..4`/`0..n`) → delete → post-delete re-select with the renumbered `data-id`.
  - **Double-click a connection → inline text edit**: the LiveMaidEditor timing-based double-click router resolves the double-clicked `.relation` / `.class-relation-hit-target`'s `data-id`. A UML relationship (`id_<Src>_<Dst>_<N>`) → opens the shared `ClassTextEditor` (`kind:"relationship"`, centered, placeholder "Label") at the click point to edit its `: label` via `setClassRelationshipLabel` (empty clears it). A note attachment edge (`edgeNote<N>`) → opens the SAME editor as `kind:"note"` over the connected note box (`g.node[id$="-note<N>"]`) to edit the note text via `updateClassNoteByIndex`. Enter / click-outside commits, Escape cancels. The router's early-return guard bails on `[data-inline-toolbar]` so double-clicking the edge toolbar never starts a label edit.
- **Deferred (not yet implemented)**: free drag-to-move of the title/notes on the canvas (fights Mermaid's auto-layout — Mermaid owns class/title/note positions). Title and note TEXT are editable via double-click; note→class linking is supported via the note's drag handle (see above); relationship type/cardinality/delete are editable via the edge toolbar and the relationship label via double-click (see above).
- **Global editor split default**: the code (Monaco) panel's `defaultSize` is `26%` (canvas `74%`, `minSize` `15`) for ALL diagram types — a deliberately smaller code pane so the canvas dominates. There is no `autoSaveId` on the `ResizablePanelGroup`, so `defaultSize` is the effective global default (no per-user persistence).
